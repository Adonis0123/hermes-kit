# ADR 0001：私有源仓库，按白名单导出发布

- 状态：已采纳
- 日期：2026-09-23

## 背景

技能、插件和记忆笔记每天在两个私有仓库里编写和使用：私有配置仓（Hermes 专属技能、插件、记忆）和私有共享技能仓（所有 agent 共用的技能）。这些仓库里通用内容和个人、公司细节混在一起：聊天 ID、本机路径、内部项目名、同事姓名。

其中一部分对别人有用。发布时不能泄露私有数据，现在和历史记录里都不能；也不能出现一份与实际在用版本逐渐脱节的副本。

## 决定

- 私有仓库保持唯一事实来源。公开仓库（`hermes-kit`、`adonis-skills`）是产物。
- 在原处脱敏，只保留一份。通用内容留在 `SKILL.md`；个人或公司细节移到 `references/local-*.md`（或本地配置），`SKILL.md` 写明“如果 `references/local-*.md` 存在就读取”。私有安装的行为不变。
- 导出脚本只复制白名单里的路径，并始终排除 `**/local-*`。
- 写入前，导出先跑隐私扫描：带通用规则的 gitleaks，加上只存在于私有仓库的个人禁用词表。
- 每次导出在公开仓库里是一个新提交，不带任何私有历史。
- 公开仓库在 CI 里再跑一次通用扫描。
- 第三方技能从不复制，只给链接和安装命令。

## 考虑过的方案

- **对私有仓库用 `git filter-repo`。** 可以改写历史去掉路径，但任何旧提交里漏掉的秘密都会公开。白名单实际上也会退化成黑名单。
- **`git subtree split`。** 保留某个子目录的历史，泄露风险相同，还需要私有仓库没有的干净目录边界。
- **Copybara。** 正是为这种场景设计的，支持转换和历史映射，但为两个小仓库引入 Java 工具链和配置不划算。
- **公开仓库做源，私有 overlay 叠在上面。** 对贡献者最清晰，但日常修改发生在私有安装里。每次改动都要来回同步，私有细节也仍然需要地方存放。

## 影响

- 公开的 `skills/` 和 `plugins/` 是生成的。在那里手工修改会被覆盖；贡献者提 issue 或 PR，改动落到源仓库。
- 公开历史是一串导出提交，不是真实的编辑历史。
- 新技能要先加进白名单并通过扫描，才会发布。
- 个人禁用词表从不公开，所以公开 CI 只能发现通用泄露。私有端的扫描是主要关口。
